# BMS Firmware (C)

Core logic of a **battery management system** for a 96s EV battery pack, written in the style of
embedded firmware. It uses C99, integer-only arithmetic, no dynamic memory and a hardware abstraction
layer. The firmware runs on a PC against a simulated battery ("plant model") and is covered by host-side
unit tests.

## What it does

| Function | Details |
|---|---|
| **State machine** | `INIT → STANDBY → DRIVE / CHARGING → FAULT`. Faults are **latched**: leaving FAULT needs all faults cleared, ignition off **and** a reset request. Contactors are closed only in DRIVE/CHARGING |
| **Protection** | Cell over-/under-voltage, over-temperature, over-current, sensor plausibility (open/short sense wire, NTC open circuit) |
| **Debounce + hysteresis** | A fault sets after 3 consecutive samples (30 ms) and clears after 10 (100 ms). Separate set/clear thresholds (e.g. OT sets at 60 °C, clears below 55 °C) |
| **SOC estimation** | Initial SOC from an **OCV lookup table** with linear interpolation, then **coulomb counting** in µAs (`int64_t`), so there is no drift from float rounding |
| **CAN** | Generic Intel/little-endian **bit packer**. `BMS_Status` (0x100) with 4-bit alive counter and **CRC-8 SAE J1850**, same layout as `ev_network.dbc` |
| **TX queue** | Lock-free **single-producer/single-consumer ring buffer** (power-of-two, free-running indices) with overrun counting |
| **Scheduling** | Super loop: 10 ms BMS task, 100 ms CAN task |
| **HAL** | `include/hal.h` separates the logic from hardware. `hal/hal_sim.c` is the PC implementation. An MCU port only replaces this file |

## Build & run

Requires `gcc` and `make` (Linux, WSL, macOS, or MSYS2/MinGW on Windows).

```bash
make test         # 14 unit tests (207 checks)
make test-asan    # same tests with AddressSanitizer + UndefinedBehaviorSanitizer
make              # builds bms_sim
./bms_sim overtemp 15 bms_can.log
```

Scenarios: `normal`, `overtemp` (cooling failure), `overvoltage` (one cell drifts while charging),
`sensor` (temperature sensor open circuit).

```
BMS sim | scenario=overtemp | initial SOC 79.6 %
[  0.000s] INIT     -> STANDBY   faults: none | Tmax 29.9 C, Vcell 3991..3997 mV, I 0.0 A, SOC 79.6 %
[  0.500s] STANDBY  -> DRIVE     faults: none | Tmax 29.9 C, Vcell 3991..3997 mV, I 0.0 A, SOC 79.6 %
[  7.350s] DRIVE    -> FAULT     faults: OVERTEMP | Tmax 60.1 C, Vcell 3957..3963 mV, I 80.0 A, SOC 79.4 %
[ 13.000s] FAULT    -> STANDBY   faults: none | Tmax 40.3 C, Vcell 3989..3995 mV, I 0.0 A, SOC 79.4 %
Done: 150 CAN frames sent, 0 queue overruns, final state STANDBY
```

The CAN frames are written in **candump log format** (`(0.100000) vcan0 100#9FFA0E0000451149`).
The companion **ev-can-sim** project decodes them with the DBC and verifies every CRC/counter:

```bash
python ../ev-can-sim/tools/decode_log.py bms_can.log   # -> 150 frames decoded, 0 E2E errors
```

The unit test `test_status_frame_matches_dbc` also checks the encoder byte for byte against a
reference frame generated by `cantools` from the same DBC.

## Coding rules applied

- C99, compiled with `-Wall -Wextra -Wpedantic -Wshadow -Wconversion -Werror`
- No `malloc`/`free`. All state is static or caller-owned
- No floating point in `src/`. Fixed-point units are in the names (`_mv`, `_ma`, `_dc` = deci-°C, `_dpct` = 0.1 %, `_uas`)
- Explicit casts, `u` suffixes, `default:` branch that fails safe (→ FAULT)
- Compile-time assertion for the queue size

## Layout

```
include/bms_config.h   thresholds, timing, pack configuration
include/bms.h          BMS types and API          src/bms.c       state machine, protection, SOC
include/can.h          frame, bit packing, CRC, queue   src/can.c
include/bms_can.h      BMS_Status encode/decode   src/bms_can.c
include/hal.h          hardware abstraction       hal/hal_sim.c   PC plant model + candump logger
src/main.c             super-loop scheduler
tests/test_main.c      unit tests
```
